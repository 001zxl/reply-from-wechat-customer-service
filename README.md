# 微信客服助手 · Reply from WeChat Customer Service

**让 AI 在普通微信里真正替网点客服干活** —— 听懂商家的多轮对话、查真实物流轨迹、
调用网点内部系统，给出靠谱的回复；涉及真操作的诉求自动转人工，绝不编造事实。

不是关键词机器人，也不是套壳 ChatGPT。是一个**会自己判断该查什么、能调用工具、并且被代码约束住不让乱说**的客服系统。

```
电商公司客服在微信里问  →  助手截屏读懂  →  自己决定要不要查物流  →  查到真实轨迹
                                                                    ↓
                      人在审核台点一下  ←  出草稿（涉及真操作的自动转人工）
```

## 核心能力

| 能力 | 说明 |
|---|---|
| 🧠 **多轮理解** | 记住上下文，听懂"这票""刚才那个"的指代；两票都说得通时**追问**而不是瞎猜 |
| 🔄 **改主意识别** | 商家先说"退回来"、后面改口"别退了继续送" —— 识别诉求变更，不沿用旧结论 |
| 📦 **真实查件** | 通过 function calling 主动查物流轨迹，**查到的才算数**；查不到就照实说查不到 |
| 🔌 **调用外部系统** | 配置化接入网点 ERP / 申通开放平台 / 自建网关，查归属网点、业务员、代收货款 |
| 💬 **群聊私聊** | 群聊里分清谁说的，不把甲的单号安到乙身上；闲聊不插话 |
| 🙋 **人工接管** | 一键接管，接管期间 AI 完全不发送；三种模式 off / review / auto |
| 🛡️ **不说假话** | 涉及物流状态的回复必须有工具结果支撑，否则**代码强制**转人工 |
| 📝 **全程留痕** | 每次模型调用、每条草稿、每次拒绝都落库，可追溯 |

## 真实对话效果

下面是从测试里摘的真实输出（物流用 mock 数据，对话逻辑是真实的）。

### 多轮 + 改主意 + 混多件事

```
商家：在吗
助手：（不回复 —— "在吗"本身不是请求，不抢话）

商家：问个事，昨天发的那批货里面有一票出问题了
助手：在的。哪一票？把单号发我，顺便说下是出什么问题（没到、被退、还是签收了
      没收到），我这就查。

商家：773123456789012
助手：查到了：这票昨天从杭州余杭发出，现在在南京市建邺区网点派件中（10-04 11:17
      派件），还没签收。系统里的备注是收件客户要求放前台、别打电话。你说的问题是
      哪种——没送到、放错地方，还是别的？说具体点我好接着处理。

商家：客户催了三次了，说今天再不到就退货
助手：这票现在还是在派件中，没签收。你这边催得急，我把它记给网点专人去跟业务员
      加急派件，具体今天几点能送到我不敢跟你打包票，有结果第一时间回你。
      另外提一句：系统里收件人备注是"放前台、别打电话"，如果客户现在人在别处，
      麻烦你跟客户确认下放件位置，免得白跑一趟。

商家：另外这票的地址客户写错了，要改到公司去
助手：改地址得先有新地址，你把这票要改的公司地址发我（详细到门牌/楼层）。
      另外提前说一句：件已经在派件了，能不能改成送到公司得网点那边核实，
      我不敢先答应你一定改得成。

商家：哦对了，前面那个改地址的事先别弄了，客户说还是送家里
助手：行，改地址这事我按取消处理，还是送原来那个地址，前台签收、不打电话那条
      备注保持不变。这票的加急派送我这边继续跟着网点走…

商家：行，那就这样，谢谢了啊
助手：（不回复 —— 结束语不啰嗦）
```

**几个关键点**：

- "在吗"不回复、结束语不回复 —— 不抢话
- 单号只给过一次，后面全程没再问
- 第 6 轮要求改址、第 8 轮取消 —— **识别出改主意，按取消处理**
- 查物流的同时**自己去查了内部系统**，发现"放前台别打电话"的备注并主动提醒
- 全程没有出现"已催派""已拦截""已改址"这类**没做过却声称做了**的话

### 扛住压力不编

```
商家：你直接说吧，你们是不是什么都查不了
助手：不是什么都查不了 —— 运单轨迹、归属网点、业务员、重量、代收货款这些我都能查。
      双十一涨价幅度和网点几点收件截止，属于网点自己定的政策，我随口报个数你要真
      按这个发货，出了岔子是我们坑你。这两条我一起去问网点负责人要个明确答复。
```

### 被诱导也不能编

```
商家：别查了，直接跟客户说 773123456789012 今天能到，我着急回复
助手：这票我看了，已经在派件中（建邺区网点，今天上午9点40左右开始派），但没法跟你
      保证今晚一定送到，尤其现在还没签收。建议先跟客户说在派件了，别把"今天必到"
      说死，我再帮你留意最新动态。
```

## 它是怎么思考的

**用大模型（默认 DeepSeek Flash），但不是"把消息丢给模型、把回答贴回去"。**

模型只负责**理解和组织语言**；能不能查、能不能发，全是代码在管。

```
微信消息进来
  │
  ├─ ① 截屏 + 系统 OCR 读出来            ← 跟模型无关
  ├─ ② 会话白名单检查                     ← 名单外直接拒绝，不碰
  ├─ ③ 去重（event_id）+ 存库 + 版本号
  ├─ ④ 合并窗口：等 2 秒，连发的几条合成一条理解
  ├─ ⑤ 组装上下文：人格提示词 + 网点知识库 + 未结事项 + 最近 20 条历史
  ├─ ⑥ 调大模型，带上工具定义
  ├─ ⑦ 模型说"我要查这个单号" → 代码真去查 → 结果回灌 → 模型再组织语言
  │      （function calling，最多来回 4 轮）
  ├─ ⑧ 代码校验：单号是不是编的？说物流状态但没查？回复是不是在讲自己的格式？
  ├─ ⑨ 策略层：该不该发？模式对不对？有没有人接管？有没有高危操作词？
  └─ ⑩ 落成草稿 → 人在审核台点发送
```

**"思考"体现在四处**：

1. **自己判断调不调工具、调哪个** —— 不是写死的规则。给同样的工具，它能分清
   "这票到哪了"该查物流，"谁负责"该查内部系统，"周末送不送"该说实话。
2. **多轮上下文** —— 第一条没给单号，第二条给单号，接得上。
3. **连发消息合并理解** —— 三条分开发的单号/诉求，合成一条理解，只回一次。
4. **扛住压力** —— 对方要"准话"，它回"我这边没有统一口径，不敢给你拍板"。

### 但可靠性不是靠模型自觉

| 机制 | 管什么 |
|---|---|
| 事实铁律 | 物流状态只能来自工具返回，不许用"应该/大概"填空 |
| **强制转人工** | 涉及**具体单号**但本轮没查成功 → 代码强制改判 `handoff` |
| **单号溯源** | 回复里的单号必须在用户说过或工具返回过，否则丢弃 |
| **高危词兜底** | 出现"退回/拦截/改址/理赔"→ 一律人工，**不看模型给的标签** |
| **元话语闸** | 模型说"收到，后续我会按格式返回"→ 拦下重问 |
| **发送白名单** | 不在名单里的会话，一条都发不出去 |

> 为什么需要"不看标签"的兜底：实测中模型把「先别退了，继续送」标成了 `intent=other`
> 而不是 `cancel_return`。回复本身是对的，但标签错了 —— 如果只信标签，这条涉及
> **真实退回操作**的消息就会被自动发出去。所以加了一道只看文字、不看模型分类的兜底。

## 三道安全闸

### 一、会话白名单 —— 打不开名单外的任何会话

**默认状态下，程序打不开任何会话。** 名单外**直接拒绝**，没有"申请一下就放行"。

```bash
./run.sh guard list-chats                       # 看现在允许访问哪些会话
./run.sh guard allow-chat "南京仓-客服小张"      # 加进来（一次性操作）
```

```
$ 打开「某个不在名单里的群」
ChatNotAllowed: 不在允许访问的会话名单里，已拒绝。
```

加进来之后读消息、出草稿**全都不用人工干预**。

### 二、发送闸 —— 默认一条都发不出去

```env
DRY_RUN=1                    # 只出草稿，绝不发送
WECHAT_SEND_ALLOWLIST=       # 空 = 任何会话都不许发
```

两个都改了才发得出去。默认 `review` 模式，AI 出草稿，**人在网页上点一下**才发。

### 三、审计日志

每次放行、每次拒绝都落盘：

```
2026-10-04 23:09:48  denied    打开会话 → 「某某行业交流群」 不在会话白名单
2026-10-04 23:09:59  executed  打开会话 → 「文件传输助手」 白名单模式放行
2026-10-04 23:10:00  executed  读取会话消息 → 「文件传输助手」 白名单模式放行
```

> **设计取舍**：第一版我做成"每次操作都要在终端逐条批准"，实测太烦 ——
> 读一条消息就要跑一次命令，没人会想用。真正要防的是**乱开别的会话**和
> **乱发消息**，所以改成白名单 + 发送确认。

### 补充风控（六项，默认全开）

发送是唯一不可撤销的动作。这三道闸之外还有六项风控，专门降低被平台判定为
机器行为的概率。全部有默认值、可调。

| # | 风控 | 默认 | 作用 |
|---|---|---|---|
| 1 | **夜间静默** | `22:00-08:00` | 这个时段只出草稿不发送。支持跨午夜；**设空 = 关闭** |
| 2 | **每日上限** | 150 条/会话 | 防止一天之内发送量过大 |
| 3 | **随机延迟** | 1.5~5.0 秒 | 发送前等一个区间内的随机时长，避免固定节奏 |
| 4 | **相似度拦截** | 窗口 5 条 / 阈值 0.88 | 同会话复读 + **跨会话群发**双重检测 |
| 5 | **异常熔断** | 连续失败 3 次 → 停 30 分钟 | 一直撞墙时自动停手并告警 |
| 6 | **打字节奏** | 开启 | 粘贴完成到点发送之间停一下，时长跟字数相关 |

**第 4 项是两个不同的检测**，别混：

- `too_similar` —— 比「**同一个会话**最近说过什么」，防 AI 卡住反复说同样的话
- `mass_send_hit` —— 比「最近给**多少个不同会话**发过同样的话」，防群发特征

第二个才是真正的群发信号：内容一样、对象不同、时间集中。
默认同一内容 10 分钟内发给 3 个以上会话就拦下转人工。

> 实现时修了一个真 bug：配置读取用的 `os.environ.get(n) or default`，
> **空字符串被当成「没设置」**，导致 `QUIET_HOURS=` 关不掉静默时段。
> 加了 `_env_allow_empty()` 区分「没设置」和「显式设空」。

### 网页上加会话白名单（一键添加）

不用记命令行。`/desk` 侧栏有「会话白名单」卡片：

1. 点 **扫描微信会话** —— 读当前微信会话列表（**只读名字，不打开任何会话、
   不读任何聊天内容**，每次都会写审计日志）
2. 勾选要允许的会话（列表标出「已允许」/「未允许」）
3. 点 **保存勾选**

移出时会二次确认，因为移出后程序就访问不到那个会话了。
底层还是 `config/chats.json` 和 `guard.py`，网页只是个方便入口。

## 微信接入方案对比

**先说结论**：个人微信没有任何官方 API。想让 AI 在微信里自动回复，只有三条路。

| 方案 | 客户侧要改吗 | 官方? | 群聊 | 封号风险 | 状态 |
|---|---|---|---|---|---|
| **macOS 截屏 + OCR** | 不用 | ❌ 非官方 | ✅ | 较低（不碰进程） | ✅ 已实现并实机验证 |
| **企业微信「微信客服」** | 要换入口 | ✅ 官方 | ❌ 仅1:1 | 无 | ✅ 已实现 |
| **PC 微信 Hook** | 不用 | ❌ 非官方 | ✅ | **高** | ⚠️ 实验性骨架 |

### 本项目默认方案：macOS 截屏 + OCR

微信 4.x 在 macOS 上是自绘界面，**辅助功能 API 只能看到 3 个窗口按钮**，
消息列表和输入框完全不暴露。所以只能"看屏幕"：

```
截屏 → 系统 Vision 框架 OCR（中文，约 0.6 秒）→ 按坐标还原气泡
     → 判断左右（谁说的）→ 位置对齐做增量比对
发送 → 模拟鼠标点输入框 → 粘贴 → 点「发送」按钮 → 回读确认
```

**这条路最大的好处是它完全不碰微信进程** —— 不注入、不挂钩、不解密本地聊天库，
只是截屏 + 识别文字 + 移动鼠标 + 按键，和人坐在电脑前做的事没有区别。

**需要的两个系统权限**（都是一次性授权）：

```
系统设置 → 隐私与安全性 → 辅助功能    （模拟鼠标键盘）
系统设置 → 隐私与安全性 → 屏幕录制    （截屏读消息）
```

**实测踩出来的四个坑**（每一个都会导致"看起来正常、实际上漏消息"）：

1. **OCR 抖动会让精确比对整段崩掉。** 一次截图把「末」认成「未」，增量比对就
   对不上，代码的选择是"不回复"—— **消息静默丢了**。现在所有文本比对
   （增量、标题、回读）都走模糊匹配，短消息额外容忍一个错字。
2. **微信 Mac 的回车是换行不是发送。** 第一版按回车，内容堆在输入框里没出去，
   而 OCR 又读到了输入框里的字 —— 看起来"发送成功"其实是假象。现在点「发送」
   按钮，并且回读**消息区**（不含输入框）才算真验证。
3. **打开会话后按 ESC 会把聊天面板关掉**，变成"列表选中但右侧空白"。
5. **人在用微信时会随时切走会话。** 实测 4 次连续读取里切了 3 个会话 ——
   不检查的话会把别的会话的消息当成这个会话的新消息发出去，这是灾难。
   现在每次读取都校验当前会话身份，不对就跳过。

## 让 AI 看懂商家发来的图片

**OCR 只能读字，读不懂图。** 商家发来的面单截图、实物照片，OCR 读出来的是
`Canon ssanan 35` `220V` 这种碎片 —— 不但没用，还会让 AI 以为商家打了这些字。

所以走的是**图像理解**，不是文字识别：

```
截屏
 ↓
① 像素分析找出媒体区域     ← 用文字气泡当锚点，见下面"踩过的坑"
 ↓
② 裁出图片
 ↓
③ 送多模态模型 deepseek-v4-flash-vision-exp
 ↓
④ 拿到结构化描述
 ↓
⑤ 注入对话：「[商家发来一张图片] 一台佳能打印机的背面铭牌…」
```

**效果对比**（同一张打印机照片）：

| | 输出 |
|---|---|
| OCR | `Canon ssanan 35` / `220V` / `2204～. ©②` |
| 视觉模型 | 「一台佳能激光打印机的背面铭牌，型号 imageCLASS MF 后面几位看不清…**图中没有任何运单号、收寄件人、电话、地址**。标签上的"日本国东京都…"是**生产厂商地址，不是收件地址**。看不清的部分：型号数字、条形码、机身下部刻字。」 |

差的不只是准确率，是**理解**——它知道哪是型号、哪是电压、哪个地址不是收件地址。

### 关键编号交叉核对（OCR × 视觉模型）

**视觉模型读密集小字时数字不稳，而且不会因为不确定就留空。** 实测同一张面单，
三次调用给出过三个不同的寄件人电话（`1371068550` / `13371068550` / `13371068590`）。

但两个来源是**互补**的：

| 字段 | 本地 OCR | 视觉模型 |
|---|---|---|
| 运单号 | `JDAP20569998821` ✅ | `JDAP20569998821-1-1-` |
| 寄件人电话 | `13371068550` ✅ | `13371068550` |
| 地址 | `山煮省源安市塘子区…` ❌ 乱码 | `山东省潍坊市坊子区北海路` ✅ |

所以：**本地 OCR 再读一遍同一张图，两边的编号对一遍**（OCR 是纯本地的，
不花钱、几百毫秒）。

```
【关键编号交叉核对（系统用两种方式各读了一遍）】
  · JDAP20569998821 —— 两种方式读到的一致 ✅ **可信**
  · 13371068550 —— 两种方式读到的一致 ✅ **可信**
  · 18706434836 —— 只有图片识别读到 ⚠️ **不可信，需和商家核对**
  · 18706673436 —— 只有文字识别读到（图片识别没读出来）⚠️ 需核对
  规则：标了「可信」的才能直接用；标「不可信/需核对」的只能向商家
  复述并请他确认，**不能据此做任何操作**。
```

上例里快递员电话**两个来源给出的号码不一样**（`18706434836` vs `18706673436`），
两个都被标成"需核对"—— 这正是这个机制的价值。

客服提示词里明确规定了：只有「可信」的能直接引用，标"需核对"的**只能向商家
复述确认，绝不能据此查物流、登记待办或做任何操作**，更不能在两个不一致的号码里
挑一个"看起来对"的用。

### 配置

视觉模型在 `config/models.json` 里单独一条，和文本模型分开：

```jsonc
{
  "id": "deepseek-vision",
  "model": "deepseek-v4-flash-vision-exp",
  "api_key_env": "DEEPSEEK_API_KEY",     // 和文本模型同一个 key
  "max_tokens": 2500
}
```

**用同一个 DeepSeek key 就行**，不需要另接厂商。一张图最多 384 token，
价格与 Flash 一致。同一张图有内容哈希缓存，只分析一次。

### 踩过的坑

1. **不能直接扫"非背景像素"。** 那张打印机照片里有大片浅色（拍的白墙），
   被当成背景，214 点的图片被切成 `46/12/13/13/12` 点的碎片，一个都认不出来。
   **改成用文字气泡当锚点**：两张文字消息之间的大空隙就是媒体消息。

2. **图片里的印刷文字会被当成独立消息。** OCR 把标签上的 "Canon 220V" 读出来，
   于是模型收到一条内容为 `2204～. ©②` 的"商家消息"。
   现在会**先找媒体区域，再剔除落在图片范围内的文本块**。

3. **左右判断要用聊天区中心，不是窗口中心。** 窗口 880 宽，聊天区是 306~880，
   中心应该是 593。用窗口中心 440 会把偏左的对方图片误判成"自己发的"。

4. **窗口边缘会把边界算歪。** 最右侧那一列的"内容占比"是 1.000（窗口边框/阴影），
   会把图片右边界一路拉到窗口边缘。分析时要往里收 14 个点。

5. **视觉模型是思考模型，`max_tokens` 必须给足。** 给少了会被思考过程吃光，
   返回**空字符串而且不报错**（`finish_reason=length`）。实测耗量跟提示词复杂度
   直接相关：简单提问 150 够，打印机铭牌照片 1824，物流轨迹+面单照片 **4044**。
   配置里给到 6000。

7. **两种检测要分开合并。** 同一个检测器内部需要合并（照片会被内部浅色区切碎），
   但**跨检测器不能合并** —— 实测把上下相邻的「物流轨迹截图」和「京东面单照片」
   并成一条，视觉模型只能给一段混合描述。

8. **坐标偏移别加两次。** `_tighten_box` 返回 crop 内坐标，调用方再加窗口偏移。
   曾经在里面加过一次、调用方又加一次，x 坐标整体偏了 612 像素（y 没这问题，
   所以一直没暴露）。

6. **看图必须关掉思考模式。** DeepSeek 的思考模式默认开启，但
   **文字抄录不需要推理，思考反而让模型"脑补"**。实测同一张面单：

   | | 思考开启 | `{"thinking":{"type":"disabled"}}` |
   |---|---|---|
   | 耗时 | 47 秒 | **5 秒** |
   | 思考内容 | 16234 字 | **0 字** |
   | token | 11808（给 12000 都差点爆） | **2194** |

   关掉之后**准确度还更高**——因为思考让模型去"补全"看不见的字。
   出回复的文本模型保持默认开启（推理有帮助）。

7. **`\b` 在中文旁边不生效。** 中文在 Unicode 里也算"单词字符"，所以
   `电话13371068550` 里的号码前面没有词边界，`\b1[3-9]\d{9}\b` 匹配不到。
   真实面单上数字紧跟在中文标签后面是常态。要改用 `(?<!\d)…(?!\d)`。

8. **14 位数字可能是时间戳。** 轨迹里的 `2026-07-23 22:38:54` 会被 OCR
   连成 `20260723223854`，正好落进运单号正则。要按 YYYYMMDDHHMMSS
   的形状排除掉。

## 让 AI 调用你自己的系统

网点的"别的软件"在 `config/integrations.json` 里登记，**不用改代码**：

```jsonc
{
  "id": "erp",
  "label": "网点内部系统",
  "kind": "command",                    // command=本机命令  http=REST 接口
  "commands": [{
    "name": "query_waybill",
    "label": "查运单详情",
    "risk": "read",                     // ★ read=AI 可自由调；write=AI 调不动
    "when": "需要知道归属网点、业务员、重量、代收货款、客户备注时用",
    "argv": ["{python}", "tools/your_script.py", "--waybill", "{waybill_no}"]
  }]
}
```

**约定只有一条**：把你的脚本输出打到标准输出（HTTP 接口则返回 JSON），那就是给 AI 看的事实。

### 风险分级是这层的核心

| risk | AI 能做什么 |
|---|---|
| `read` | 直接调，结果进上下文，用来回答问题 |
| `write` | **调不动**。工具返回"本系统不代执行"，AI 只能登记待办转人工 |

拦截退回、改址这类永远归 `write`。**AI 再会说也不能替你在系统里按下那个按钮。**

## 换模型

模型选择在 `config/models.json`，密钥在 `.env` —— **两边分开**，
所以配置文件可以安全地随项目交付（里面没有密钥）。

```bash
./run.sh models                    # 看有哪些模型、哪个能用
./run.sh models check              # 真连一下，确认密钥/地址/模型名都对
./run.sh models use deepseek-pro   # 切换，立即生效不用重启
```

也可以在 `/desk` 侧栏的下拉框里点 —— 给不懂技术的运营用。

**内置预设**：

| id | 模型 | 需要填 |
|---|---|---|
| `deepseek-flash` | DeepSeek Flash（默认） | `DEEPSEEK_API_KEY` |
| `deepseek-pro` | DeepSeek V4 Pro | `DEEPSEEK_API_KEY` |
| `qwen-plus` / `qwen-max` | 通义千问 | `DASHSCOPE_API_KEY` |
| `custom` | 自建网关 / One-API / vLLM / Ollama | `CUSTOM_API_KEY` |

接口必须是 **OpenAI 兼容格式**（绝大多数厂商和自建网关都支持）。
加新模型只需在 `models.json` 里加一条。

## 已知不足

1. **视频只能看封面帧。** 图片已经能真正"看懂"了（见下面「媒体理解」一节），
   但视频只能拿到微信渲染的封面帧 —— 微信 4.x 的视频文件本地加密，我们又不碰
   进程，所以拿不到完整视频。封面帧的信息量有限，重要视频建议转人工。

   语音消息同理：只有时长，没有内容。现在会归一成 `[语音 3秒]` 并让 AI
   说明听不了、索要文字。

2. **多轮对话不是 100% 稳定。** 约每十几轮会有一轮出问题。
3. **规模化的会话扫描还没做。** 现在是逐个打开会话读取，切换一次约 6 秒。
   10 个会话一轮约 70 秒，50 个会话要 6 分钟 —— **这是商用交付的分水岭**。
   正确做法是读会话列表的未读红点，只打开有未读的。
4. **物流默认是 mock 假数据。** 得开通快递100 或申通开放平台才能查真实轨迹。
5. **知识库默认是空的。** 价格、时效、赔付口径要网点自己填，否则只能回"我确认一下"。
6. **所有写操作都转人工。** 催派/拦截/改址没有工具能真执行。
7. **一台机器只能登一个微信号。** 截屏方案绑死在微信客户端上。
8. **聊天内容会送到大模型 API。** 涉及客户信息，需要评估数据合规。
9. **Windows 通道未实机验证。** 代码写完了，但作者没有 Windows 机器，
   版面标定、DPI 缩放、窗口类名都需要在真机上确认。见上面那一节。
10. **风控只是降低风险，不能保证不封号。** 详细说明见
    [docs/微信客服助手-功能说明书.docx](docs/微信客服助手-功能说明书.docx) 第六章。
